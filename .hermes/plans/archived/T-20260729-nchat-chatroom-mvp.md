# nchat MVP 技术规格书 — 去中心化 P2P 聊天室

**版本**: v0.1-mvp
**状态**: 已实现
**目标**: 构建一个可在局域网/互联网中使用的去中心化 P2P 聊天室参考实现

---

## 一、核心哲学（Agent 必须理解的前提）

1. **这不是一个"聊天软件"，而是一个"神经元连接"的可感知 Demo**
   - 用户打开网页后自动发现附近/n 同一网络中的其他用户
   - 能创建房间、搜索房间、发送消息
   - 整个过程中没有任何中心服务器存储用户数据

2. **MVP 优先跑通，不求完美**
   - 先用最小可行方案验证"节点发现 + 命名解析 + P2P 通信"三条核心链路
   - 生产级优化（NAT 穿透、断线重连、大规模并发）在后续版本处理

3. **协议中立**
   - 当前版本聚焦聊天体验，但底层数据结构要为未来扩展（游戏、广播、文件传输等）预留空间

---

## 二、技术栈

| 层面 | 选型 | 原因 |
|---|---|---|
| 构建工具 | Vite 5+ | 零配置、HMR 快、PWA 支持好 |
| 前端框架 | Vue 3 + Composition API | 参考实现，轻量、生态成熟 |
| P2P 传输 | **PeerJS**（封装 WebRTC DataChannel） | MVP 阶段比 js-libp2p 简单 10 倍，WebRTC 连接一行代码 |
| 信令服务 | 自建轻量 **PeerJS Server**（可部署到 Cloudflare Workers 或自托管） | 仅初始化握手时工作，不参与数据传输 |
| 本地持久化 | IndexedDB（通过 idb 库） | 存储 PeerID、已发现节点、最近消息缓存 |
| 样式 | 纯 CSS / UnoCSS | 轻量、无额外依赖 |

**为什么 MVP 用 PeerJS 而非 js-libp2p：**
- PeerJS 将 WebRTC 的信令握手 + DataChannel 封装为一行 `peer.connect(id)`
- 跑通"两个浏览器互相发现并发消息" 10 分钟可完成
- js-libp2p 在浏览器端的 WebRTC 配置复杂，调试时间长，不适合 MVP 阶段
- 后续版本可平滑迁移到 libp2p，PeerJS 只作为信令+传输的抽象层

## 四、数据模型与协议格式

### 4.1 PeerID

```
PeerID = ed25519 公钥的 Base58 编码
首次启动用 crypto.subtle.generateKey() 生成 Ed25519 密钥对
公钥作为 PeerID，私钥用于消息签名
```

**持久化**: 生成后存入 IndexedDB，同一浏览器刷新后复用同一 PeerID

### 4.2 消息格式（JSON over WebRTC DataChannel）

```json
{
  "type": "message_type",
  "from": "<sender_peerid>",
  "to": "<room_name>",
  "payload": { },
  "timestamp": 1745880000000,
  "signature": "<base64_signature>",
  "extensions": {}
}
```

### 4.3 核心消息类型

| type | payload | 用途 |
|---|---|---|
| `hello` | `{name: "ale160"}` | 广播自身存在，向周围节点打招呼 |
| `join_room` | `{room: "ale160", password?: string}` | 加入某个房间 |
| `leave_room` | `{room: "ale160"}` | 离开房间 |
| `room_message` | `{room: "ale160", text: "你好"}` | 聊天消息 |
| `room_list` | `{rooms: [{name, member_count, activity}]}` | 回复房间列表查询 |
| `query_rooms` | `{keyword?: "ale"}` | 搜索房间 |
| `history_request` | `{room: "ale160", since: timestamp}` | 请求历史消息 |
| `history_response` | `{room: "ale160", messages: [...]}` | 回复历史消息 |
| `heartbeat` | `{}` | 心跳保活 |

### 4.4 房间命名与发现

- 房间名是**字符串标识**，不要求全局唯一
- 搜索"ale160"时，返回当前网络中所有叫"ale160"的房间列表
- 排序规则：在线成员数 > 最近消息时间 > PeerID 字典序（作为稳定决胜）
- 每个节点本地维护房间列表，不依赖全局注册表

## 五、网络拓扑

### 5.1 MVP 网络结构

```
[信令服务器] — 仅用于 WebRTC 握手，不负责任何数据传输
      |
[节点 A] ←→ [节点 B]  (WebRTC DataChannel 直连)
   |
[节点 C]              (星形拓扑，每个新节点与信令服务器上已知节点直连)

后续版本增加中继转跳：A ←→ Relay ←→ D（NAT 穿透失败时）
```

### 5.2 节点发现流程

```
1. 节点 A 启动 → 连接信令服务器 → 获得自身 PeerID
2. 节点 A 广播 hello → 向所有已连接节点发送自身信息
3. 收到 hello 的节点回复自身的 hello + 已知的房间列表
4. 节点 A 将这些信息存入本地 IndexedDB
5. 当节点 A 搜索房间名时 → 在本地缓存中查询 → 返回匹配结果
```

### 5.3 局域网发现（后续迭代）

对于完全离线的局域网场景，后续引入：
- **mDNS / 局域网 UDP 广播**：在本地网络广播自身 PeerID
- **WebRTC LAN discovery**：利用 ICE 的 host candidate 发现同一子网的节点
- **渐进增强**：有互联网时用信令服务器，无互联网时回退到局域网广播

## 六、UI 设计指引

### 6.1 界面结构

```
┌─────────────────────────────────────┐
│  [nnet]                              │
│  你的 ID: 3J9d...K2v1    [复制]     │
│  信令服务器: https://...            │
├─────────────────────────────────────┤
│  [  搜索房间... ]           [连接]  │
├─────────────────────────────────────┤
│  房间列表（按活跃度排序）           │
│  ┌─ ale160 (5人在线)               │
│  │  ale160 (3人在线)               │
│  │  random-chat (2人在线)          │
│  └─ xxxxx                           │
├─────────────────────────────────────┤
│  当前房间: ale160                   │
│  ┌──────────────────────────────┐   │
│  │ [10:23] alice: 大家好        │   │
│  │ [10:24] bob: 你好 👋         │   │
│  │ [10:25] ale: 测试一下        │   │
│  └──────────────────────────────┘   │
│  [  输入消息...           ] [发送]  │
├─────────────────────────────────────┤
│  在线: alice, bob, ale              │
└─────────────────────────────────────┘
```

### 6.2 核心交互

1. **首页**：显示自身 PeerID（可复制）+ 房间搜索框 + 发现的所有房间列表
2. **搜索**：输入房间名后显示匹配的房间，按活跃度排序
3. **加入房间**：点击房间名 → 向该房间内的其他节点发送 `join_room` → 拉取历史消息
4. **聊天**：消息被发送给房间内所有在线节点
5. **离开**：关闭标签页时自动发送 `leave_room`

### 6.3 状态指示

- 🟢 在线（节点正常响应心跳）
- 🟡 不稳定（心跳延迟 > 5s）
- 🔴 离线（心跳超时 > 15s，从成员列表移除）

## 七、部署方式

### 7.1 信令服务器

- 基础方案：官方提供公共 PeerJS Server（`0.peerjs.com`，PeerJS
  - 临时开发可用，但不可用于生产
- 推荐方案：自建信令服务器
  - GitHub: `peers/peerjs-server`
  - 部署到 Railway / Fly.io / VPS 均可
  - 资源消耗极低（仅握手时使用）
  - 单个实例可支持数千并发连接

### 7.2 前端静态页面

- Cloudflare Pages（推荐，免费套餐足够）
- GitHub Pages
- 本地 `../../dist` 目录双击 `../../index.html`

## 八、实现优先级与任务拆解

### Task 1：项目骨架 + PeerID 生成（半天）
- 初始化 Vite + Vue 3 项目
- PeerID 生成（Ed25519 密钥对）
- IndexedDB 持久化 PeerID
- 显示 PeerID 到页面

### Task 2：P2P 连接层（1 天）
- 部署信令服务器（或使用公共）
- 集成 PeerJS Client
- 两个标签页互相连接验证
- 心跳保活、断线检测

### Task 3：房间系统 + 消息通信（1.5 天）
- 创建/加入/离开房间消息协议
- 消息收发（room_message）
- 房间列表广播（hello / room_list）
- 本地房间列表维护 + 排序

### Task 4：UI 界面（1 天）
- 搜索框 + 房间列表
- 聊天面板
- 成员列表
- 状态指示

### Task 5：历史消息 + 持久化（0.5 天）
- IndexedDB 存储最近消息
- 加入房间时从在线节点拉取历史
- 消息 dedup（通过消息 ID 去重）

### Task 6：PWA + 部署（0.5 天）
- Service Worker 注册
- manifest.json 配置
- 部署到 Pages

**总计预计开发时间**: 4–5 天（单人专注）
